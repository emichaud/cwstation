How CW Station Works

The signal path end to end — how Morse comes in, gets decoded, and goes back out — with the libraries doing the work. A map for using it, understanding the design, and troubleshooting.

{% endblock %} {% block content %}

CW Station is one loop: audio in → decode → read it, and compose → key → audio out. Everything else — the simulator, the recording upload, the fldigi tap, rig control — is a different way to feed that loop or to send the audio somewhere. The signal-processing core is numpy, Django-free and testable on its own.

{# ═══════════════ THE SIGNAL LOOP ═══════════════ #}

01 The signal loop

Two lanes. On receive, audio flows left→right into your browser. On transmit, a message flows right→left back out to the air.

▶ Receive — copying the band
Radio + antenna RF off the air, demodulated to an audio tone by your receiver.
→
Sound card in The rig's audio out → your PC's line-in, sampled to numbers. sounddevice
→
Decode engine Finds the CW note, tracks its speed, turns key-downs into letters. numpy
→
Live relay Decoded batches pushed to your open tabs over a WebSocket. Channels · daphne
→
Paper tape The browser renders dits & dahs scrolling past the now line. monitor.js
◀ Transmit — putting Morse back out
Radio + antenna PTT keyed; the keyed audio drives the rig like any digital mode.
←
Sound card out The WAV plays into the rig's audio input (or your speakers). sounddevice
←
Synthesize PARIS timing, raised-cosine edges — clean, click-free CW audio. numpy
←
Compose Your text with message keys & {tags} expanded. macros.js
The engine is Django-free: apps/cw/engine/ is pure numpy with a typed event contract. Python decodes, JavaScript renders — the browser never does DSP, it just draws what the engine already resolved. That seam is why an ML decoder or a new audio source can drop in later without touching the UI.

02 Four ways to feed the decoder

The same decode engine runs no matter where the audio comes from — that's the point of the seam.

📻 A real rig

Your receiver's audio into the sound card. cw_monitor_live reads the stream, decodes it, and posts batches to the live tape. This is the real thing.

sounddevice → numpy

🎛️ The simulator

No radio? cw_simulate generates CW with adjustable speed, noise (SNR) and drift, and feeds the same live tape — so you can learn the controls, test AFC/level, and see false-positives, exactly as a real signal would behave.

numpy synth → live tape

🎚️ A recording

Upload a WAV/MP3/FLAC/OGG on the Decode page (W1AW practice files work as-is). The tone is auto-detected; the decoder adapts to the sender's speed on its own.

audio_io → numpy

🔌 The fldigi tap

Point CW Station at a running fldigi and it reads decoded text over XML-RPC — PSK31 and every other fldigi mode — onto the same tape, through the same event contract.

fldigi XML-RPC

03 Inside the decode engine

What happens between "audio samples" and "letters on the tape" — all in numpy, no radio-specific assumptions.

Find the note — detect_tone()
An FFT over the first seconds picks the CW pitch, so you don't have to dial in a tone by hand.
Envelope & key-state
Band-pass around the tone, then track energy to decide key-down vs key-up moment to moment (this is what the level/AFC controls tune).
Adaptive timing
Measure the dit length live and let it float with the sender — no fixed WPM required. Run lengths become dits, dahs, and gaps.
Morse → text
The element pattern is looked up in the international Morse tables (morse.py), including prosigns.
Emit the event contract
Out come typed events — CharEvent, ElementEvent, KeyRun — the single shape every renderer, the logbook, and replay all read.
Callsigns are pulled from the copy as it resolves, so the logbook can match a contact to the session it was heard in — and every session can replay its exact tape.

04 Rig control — reading the dial & keying PTT

Audio decoding needs no radio connection. CAT control is separate: it reads your frequency/mode and can key PTT for transmit.

Rig Setup page Pick your radio from Hamlib's catalog; CW Station starts & supervises the daemon. rigdaemon.py
→
rigctld Hamlib's control daemon on TCP :4532 — the single translator to hundreds of radios. Hamlib
→
CAT over serial USB/serial cable to the rig: read freq & mode, set PTT on/off.
→
Your radio Live panel shows the dial; the send sheet's on air toggle keys it.
Transmit path: the send sheet keys PTT via rigctld, plays the synthesized WAV out the sound card into the rig, then drops PTT. No Hamlib installed? Decode, practice, and WAV-making all still work — only live CAT needs it.

07 Troubleshooting — follow the signal

Match the symptom to the stage that owns it.

SymptomStageWhat to check
Live tape loads but never updatesLive relayThe WebSocket needs an ASGI server — running under WSGI/gunicorn drops it. Confirm daphne serves config.asgi.
Nothing decodes off the airSound card inIs the rig's audio reaching the right input device, at a sane level? Try the Simulator to prove the decode path works without hardware.
Garbled copy / random lettersEnvelope & timingTone mis-locked or too much noise. Pin the tone, raise the level/AFC threshold, or feed a cleaner signal.
Rig panel won't connectrigctld / CATIs Hamlib installed and the serial device correct? The Rig Setup stoplights show exactly which step failed.
Transmit keys but no tone goes outSound card outAudio output device + rig audio-input wiring; keep ALC low, like any digital mode.
QRZ/eQSL passwords stopped working after a redeploycredentialsThe Fernet key file wasn't persisted — it must live on a volume with the database. See the Install guide.
Still stuck? The Install & Deploy guide covers the production gotchas, and the Rig Setup stoplights isolate a CAT problem to a single step.
